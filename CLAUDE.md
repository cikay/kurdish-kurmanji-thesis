# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Install dependencies: `pipenv install --dev` (see [README](README.md#installation)).

Running the pipeline: see [README Usage](README.md#usage). In addition to what's
documented there, each stage script can be run directly, bypassing
`pipeline.py`/`config.yml` entirely — its `__main__` block hardcodes real
`data/<stage>` paths, e.g. `python clean.py` reads `data/normalize` and writes
`data/clean`.

Tests (pytest, no package structure — `tests/conftest.py` puts the repo root on
`sys.path`):
```bash
pipenv run pytest
pipenv run pytest tests/test_cleaner.py
pipenv run pytest tests/test_cleaner.py::TestSplitParagraphs::test_splits_on_blank_line
```

No linter/formatter is configured in this repo.

## Architecture

Six-stage pipeline, orchestrated by `pipeline.py`, stages/inputs/outputs documented in
[README.md](README.md#pipeline-stages). Key mechanics not obvious from that table:

- **Stage contract** (`stage.py`): every stage is a `Stage` subclass with a `name` and
  `run(input_dir, output_dir)`. `pipeline.py` builds each stage from `REGISTRY` (name →
  class), derives `input_dir`/`output_dir` purely from stage order in `config.yml`
  (`data/<stage_name>/`), and forwards any extra `config.yml` keys for a stage as
  constructor kwargs — see [README's "Adding a stage" section](README.md#adding-a-stage)
  for the full recipe.
- **Manifest handoff**: each stage reads `manifest.jsonl` from its input dir and writes
  its own `manifest.jsonl` to its output dir, carrying prior fields forward and adding
  its own (e.g. `stats` adds `word_count`). A stage that drops a record (extraction
  failure, below word-count threshold, etc.) simply omits it from the manifest it
  writes — there's no tombstoning.
- **`data/` is gitignored** in full. Pipeline outputs are never committed and are
  expected to be regenerated by running the pipeline. The exception is
  `tests/data/*.txt`, tracked separately as test fixtures (not under `data/`).
- **`clean.py` loads the GlotLID language-ID model at import time** (module-level
  `lang_model = load_lang_model()`), which downloads it from the `cis-lmu/glotlid` HF
  Hub repo on first import via `hf_hub_download`. Any test or script that imports
  `clean.py` triggers this — expect network access and a one-time download the first
  time you touch it in a session.
- **`download.py`** scrapes `tez.yok.gov.tr` with `requests`/`BeautifulSoup` in a
  multi-step flow: POST a search form (`TezSearcher`), GET the results page, then per
  thesis resolve a one-time download key and stream the PDF (`PdfDownloader`). TLS
  verification is deliberately disabled (`verify=False`, warnings suppressed) and
  browser-like headers are hardcoded — both are load-bearing for the site to respond;
  the target language is hardcoded as `Dil=11` (Kurdish) in the search payload.
- **`push_to_hub.py`** is not a `Stage` — it's a standalone CLI that reads
  `data/filter/manifest.jsonl` directly, builds a Hugging Face `Dataset`, and pushes it
  plus `dataset_card.md` as the repo's README. Requires `HF_TOKEN` in `.env` (loaded via
  `python-dotenv`); refuses to push if the target repo already exists.

## Testing conventions

Tests call private stage methods directly (e.g. `cleaner._split_paragraphs(...)` in
`tests/test_cleaner.py`) rather than only testing through `run()` — follow this pattern
for new stage tests rather than round-tripping through files.
